# Aadhyant WhatsApp console — implementation checkpoint

The operator selected an in-site console inspired by WANotifier on 13 October 2026. This replaces the retired campaign screens with Contacts, Templates, Campaigns and Reports. It is a job-campaign console, not a complete clone of WANotifier.

## Implemented

- Canonical WhatsApp contacts, campaigns, recipients and outbox are reused. The only new public table is the Meta template catalog.
- Contacts support seven-column Excel/CSV imports, numbers-only paste, lists/tags, masked identities, bounded pagination and attributed permission recording. Imports never imply marketing permission. Existing STOP and ambiguous identity cannot be overridden by reimport or admin permission entry.
- Admin-only Edge sync reads Meta template metadata with server credentials and a fixed Graph host; no provider send endpoint is called. It commits only complete bounded responses. Language and internal version are server-managed. No approval fallback is fabricated.
- The supported job template must have the existing two body parameters and exact Interested / Stop alerts quick replies. Media headers, extra/named parameters and unsupported layouts cannot be queued. Sync currently supports `aadhyant_vacancy_alert_v1`, `en`; other templates remain visible but unavailable for this job sender.
- Campaign creation selects an open public job, template, registered/imported audience and optional list/tag. Matching is advisory, permission/STOP/subscriber preferences remain authoritative. The operator explicitly reviews selected recipients and the actual synced message body before freezing the draft.
- Server approval validates the same immutable template snapshot. Schedule uses device-local input converted to UTC and canonical outbox `next_attempt_at`. Queue creation is blocked while sender readiness is false. Retry of the same operation cannot change its audience/template/time.
- Reports show actual canonical status and timestamps; they do not simulate delivery.

## Not live / operational prerequisites

This checkpoint does not deploy or restore sending. Production worker and webhook remain the retired 410 endpoints, and the scheduler remains disabled. The new configuration starts `sender_ready=false`; there is no browser toggle that can enable it. Scheduled timestamps are implemented and tested, but automatic scheduled delivery is not operational.

1. Complete the already-authorized legacy WhatsApp purge using `supabase/production/retire_whatsapp_20261013/purge.sql`. Native mutation attempts previously failed with `Invalid or expired requestState`; deletion has not been represented as complete. Last read-only evidence: three contacts, two campaigns and one queued message remain. The new migration refuses installation if any of the seven canonical WhatsApp tables contains data.
2. Obtain approval for the new production release. Install `20261013105042_whatsapp_campaign_console.sql` only after purge, deploy `whatsapp-template-sync` with JWT verification, then deploy this frontend.
3. Configure `WHATSAPP_ACCESS_TOKEN` and `WHATSAPP_BUSINESS_ACCOUNT_ID` as server secrets. Do not paste them into chat or put them in frontend/GitHub source. The new sync has not been exercised against live Meta credentials.
4. Review and restore the canonical sender/webhook implementation and minimum backend privileges, verify template parameter mapping and provider phone identity, verify signed STOP and delivery events, and configure the approved bounded scheduler. Only then set readiness through an explicitly reviewed database operation. This integration is still outstanding; readiness must not be flipped merely to unlock the UI.
5. Any live-message test requires an expressly authorized operator-controlled recipient. This checkpoint sends no real message.

Candidate subscription UI from the retired flow is not restored by this console checkpoint. Opt-in provenance can be recorded by an admin only when permission was actually received; this is not a bulk invitation bypass.

## Validation

Local PGlite tests execute the new migration and canonical campaign functions with a fake enqueue provider. They cover snapshot changes, permission provenance, STOP, list/tag filters, malformed numbers atomic rollback, schedule gating, actual reports, SQL grants and retirement-preflight rollback. Edge tests fake every network request and cover authorization, fixed-host pagination and incomplete-response atomicity. UI tests cover exact preview substitution, template freshness and schedule input. The full suite passes 378 checks; production build and `git diff --check` pass. Browser visual/authenticated production QA has not been performed in this environment.
