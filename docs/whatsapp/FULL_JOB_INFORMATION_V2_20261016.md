# Complete vacancy information in registered WhatsApp alerts

Prepared for the user's clarified requirement on 16 October 2026. This v2 revision is not deployed, submitted to Meta, or activated. The earlier live v1 remains unchanged by this development work.

## Behavior

Company/contractor/Aadhyant fills the existing vacancy form once. Admin can select that record in Automatic Alerts and click **Preview Filled Vacancy Message** to see the actual proposed message. After approval/publication, the same reusable v2 template receives all saved candidate-facing job fields automatically; there is no per-vacancy template selection or manual rewriting.

The format contains vacancy reference; company/worksite, department and role; location and openings; qualification/trade/experience/age/gender; all saved salary/earning figures; employee deductions; employer contributions/CTC provisions; duty/shifts/OT; facilities and charges; leave/holidays; employment/payroll/duration/notice; interview/joining; additional structured benefits; and the complete job description. `full-job-field-map.json` records every mapped scalar field. Closed-catalog benefits come from the canonical Candidate benefit projection. Remaining openings are calculated from canonical headcount and filled positions. Interview timestamps are explicitly shown in IST.

Each empty individual field is omitted from its section, and actual zero amounts/days are retained. The reusable template has fixed section headings: if an entire optional section is unfilled, its value explicitly says no details were supplied. No salary, benefit, interview date or entitlement is invented. This limitation is visible in the generated review example rather than promising that Meta can conditionally remove its fixed template headings.

The candidate-facing field allowlist follows the existing M050 Candidate opportunity projection. Ownership/reviewer details, account identifiers, internal feedback, applicant records and contact-table data are not included. Job description/remarks are already a candidate-visible part of the vacancy and remain subject to Admin review.

## Long information and limits

The v2 template has 15 ordered body parameters and the same View Job & Apply / Stop alerts buttons. Fixed template text is 730 characters. Each dynamic section is bounded to 1000 characters and has whitespace normalized because template parameters must be single-line values. The portal's full 2000-character description is retained across two ordered 1000-character sections; no substring is discarded. This local envelope is not a guarantee that Meta will approve or deliver every possible expanded message. Actual Meta review and an authorized owner-controlled send remain to be completed.

Oversized legacy input or a message exceeding the existing 16 KiB canonical outbox-variable budget fails closed. Admin preview reports that the record requires review; it is not silently shortened. The scoped `registered_full_v2` validator allows these public-job sections only and continues using the existing legacy validator for all other payloads. Existing protected-key restrictions and legacy 500-character rules remain intact outside this exact new envelope.

- Exact current APPROVED v2 metadata is required before enabling/preparing the new automatic alerts. Approval of v1 is insufficient.
- The setup endpoint submits only the static reviewed v2 request to the bound account, reuses an exact existing v2 template and refuses conflicting content.
- Existing canonical campaigns/recipients/outbox, standing Admin approval, subscriber consent, STOP, sender verification, batch/daily quotas, publication deduplication and no-historical-replay boundaries remain in force.
- Frozen message comparison now includes every new field and structured benefit. A changed facility, description or benefit pauses pending sends just as changed salary does.
- Automatic sending stays off; this revision makes no live publication, candidate send, consent change or scheduler activation.
